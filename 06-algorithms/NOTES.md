# 第 06 章：数据结构与算法（手写实现 + STL 对照）

> 本章的教学主线只有一句话：
> **每个数据结构都先「手写实现一遍」，再「用 STL 等价物写一遍」，然后实测对比，最后给出工程结论。**
>
> 手写的目的**不是**让你以后自己写容器，而是让你知道 STL 里那个东西内部发生了什么、
> 为什么它在某些场景快、在某些场景慢、以及你什么时候会被它的复杂度坑到。
> 结论先放在这里：**生产代码请用 STL**。理由在本章「实用开发习惯」一节展开。

所有实测数据都由本章的 `.cpp` 在 **Debug（/Od）** 下跑出来。
Debug 的绝对数字比 Release 慢很多，**请只看趋势和数量级差异，不要拿绝对值去和别人比**。

## 3. 手写 vs STL 对照总表

「实测谁快」一列的数字来自本章各文件在 Debug 下的真实输出，仅代表本机趋势。

| 数据结构 | 手写要点 | STL 等价物 | 实测谁快 | 工程结论（生产该用哪个） |
| --- | --- | --- | --- | --- |
| 动态数组 | size + capacity、1.5 倍扩容、Rule of Five、强异常保证、`T*` 迭代器 | `std::vector` | `std::vector` 快（实测 `push_back` 20 万次：手写与 STL 同量级，STL 略快；`reserve` 后快约 10%） | **用 `std::vector`**。它是 C++ 里最重要的容器，默认真空 |
| 单链表 | 哨兵头节点、`next` 指针、快慢指针 | `std::forward_list` | 顺序遍历 `std::vector` 比链表**快约 20 倍** | 默认不用链表；只在「已知位置频繁插入删除」时考虑 |
| 双向链表 | 头尾双哨兵、`prev`/`next` | `std::list` | 遍历 `vector` 完胜；中间插入删除链表才赢 | 生产极少用 `std::list`，通常 `std::vector` 或 `std::deque` 更好 |
| 栈 | 数组版（连续、快）/ 链表版（不扩容） | `std::stack`（默认底层 `std::deque`） | 数组栈最快；`std::stack` 略慢于裸数组 | **用 `std::stack`**；性能敏感且已知上限时可用 `std::vector` + `push_back` 代替 |
| 队列 | 循环队列（取模 / 位运算）、空满判断 | `std::queue`（默认底层 `std::deque`） | `std::deque` 做底层最适合（两端均摊 O(1)） | **用 `std::queue`**；需要随机访问时用 `std::deque` |
| 哈希表 | 散列函数、链地址法 / 开放寻址、负载因子、rehash、墓碑 | `std::unordered_map` | STL 快（手写版通常慢 2 到 4 倍，主要差在质数表与内存池） | **用 `std::unordered_map`**；需要有序遍历时改用 `std::map` |
| 二叉搜索树 | 插入 / 删除（三种情况）/ 中序 / 高度 | `std::map` / `std::set`（红黑树） | 有序插入 10 万条时，朴素 BST 退化到高度约 10 万，`std::map` 约 30 余；查找慢几个数量级 | **绝对用 `std::map` / `std::set`**。手写平衡树是典型的「不要重复造轮子」 |
| 二叉堆 | 数组表示、`sift_up` / `sift_down`、O(n) 建堆 | `std::priority_queue` | 同量级，STL 略快 | **用 `std::priority_queue`**；需要修改堆中元素时用 `std::make_heap` 系列裸算法 |
| 并查集 | 路径压缩 + 按秩合并 | 无（`std::` 里没有） | — | **这个真的要自己写**。STL 没有并查集，手写十几行即可，性能已接近理论最优 |
| 排序 | 九种手写实现 + 稳定性验证 | `std::sort` / `std::stable_sort` | `std::sort` 快于所有手写版本 | **永远用 `std::sort` / `stable_sort`**（除非有特殊内存或数据类型约束） |
| 图算法 | 邻接表、DFS / BFS、Dijkstra、Bellman-Ford、Kruskal / Prim | 无（`std::` 里没有图算法） | — | **要自己写**，或用 Boost.Graph。图算法是「必须会手写」的领域 |

**一句话总结这张表**：
STL 里**有的**容器和算法，一律用 STL；STL 里**没有**的（并查集、图算法、特定领域的 DP 模板），才需要自己写，
而且写的时候要按本章演示的方式做「正确性对拍 + 性能实测」。

## 4. 重点难点详解

每个难点都按同一套结构讲：**错误直觉 → 正确模型 → 代码证据 → 工程建议**。

### 4.1 均摊复杂度：`push_back` 到底是 O(1) 还是 O(n)？

- **错误直觉**：「`vector` 满了要重新分配并搬走所有元素，所以 `push_back` 是 O(n)。」
  于是得出结论「用 `vector` 频繁 `push_back` 很慢，应该用链表」。
- **正确模型**：`push_back` 的**单次最坏**确实是 O(n)，但**均摊是 O(1)**。
  关键在于扩容是**按倍数**拉长间隔的。设增长因子为 k（MSVC 用 1.5），
  总搬移次数 = n + n/k + n/k² + ... = n · 1/(1 - 1/k)。
  当 k = 2 时上界是 2n；当 k = 1.5 时上界是 3n。**都是 O(n)**。
  把它摊到 n 次 `push_back` 上，每次就是 O(1)。
  直觉版本：贵的操作越来越少，所以贵的那几次被大量的便宜操作摊薄了。
- **代码证据**（`01_complexity_and_measurement.cpp`）：在 MSVC 上 push 20 万个元素，
  实测容量序列是 `1 2 3 4 6 9 13 19 ...`（1.5 倍增长），
  **累计搬移元素次数 = 414776 ≈ 2.07n**，而不是 n²。
  同时实测：不 `reserve` 用 4771 微秒，先 `reserve` 用 4375 微秒，只快约 9%。
- **工程建议**：
  1. 不要因为「怕扩容」而放弃 `vector` 改用 `list`——那是用 20 倍的遍历代价
     换取一个本来就被摊薄掉的成本。
  2. **能预估大小时先 `reserve`**。它是零风险优化，主要价值其实不是省那 9% 的 CPU，
     而是避免扩容时的**内存峰值**（老块和新块会同时存在，瞬时占用接近 1 + k 倍）。
  3. 注意「均摊 O(1)」隐含前提：**元素类型的移动/拷贝必须是 O(1)**。
     如果元素移动是 O(n)，那么 `push_back` 就不再是均摊 O(1) 了。

### 4.2 链表为什么慢：复杂度相同，性能差 20 倍

- **错误直觉**：「链表插入删除是 O(1)，`vector` 是 O(n)，所以链表更快。」
- **正确模型**：这个比较**只对「已经持有插入位置指针」的情况成立**，
  而找到那个位置本身就要 O(n)。更致命的是**缓存局部性**：
  - CPU 从内存取数据是按 **cache line（通常 64 字节）** 整块取的。
  - `vector` 的元素连续排列，一条 cache line 能装 16 个 `int`，
    所以 16 次访问只付 1 次内存延迟；再加上 CPU **硬件预取器**能识别顺序访问模式，
    提前把后面的数据拉进缓存，实际延迟几乎被完全隐藏。
  - 链表的节点一次 `new` 一个，散落在堆的各个角落（虽然分配器会尽量让同批分配靠近，
    但经过多轮插入删除后必然碎片化），每走一步都可能是一次 **cache miss**，
    而一次 cache miss 相当于几百个 CPU 周期。而且预取器对指针追逐**完全无效**，
    因为下一个地址要等当前节点读出来才知道。
  另外链表每个节点还要多背 1 到 2 个指针，同样的数据占用更多内存、更多 cache line。
- **代码证据**（`01_complexity_and_measurement.cpp`）：同样遍历求和 20 万个 `int`，
  `std::vector` 用 306 微秒，`std::list` 用 6229 微秒，**慢约 20 倍**。
  两者复杂度完全一样，都是 O(n)。
- **工程建议**：
  - **默认用 `std::vector`**。绝大多数「我以为需要链表」的场景，`vector` 都更快。
  - 真的需要频繁在中间插入删除时，先考虑 `std::deque`（两端均摊 O(1)，且仍是分块连续）。
  - 只有在**已经持有迭代器/指针**、且插入删除极其频繁、元素很大且移动昂贵时，
    `std::list` 才可能赢。即便如此也要**先测再说**。
  - 「指针追逐」是现代 CPU 上最反模式的内存访问方式，要本能地回避。

### 4.3 哈希冲突与负载因子：平均 O(1) 不是免费午餐

- **错误直觉**：「哈希表查找是 O(1)，所以随便存多少都很快。」
- **正确模型**：O(1) 是**平均情况**，而且依赖两个前提：
  1. **散列函数把键均匀打散**。如果所有键都映射到同一个桶，
     链地址法就退化成一条链表，查找变 O(n)——最坏情况。
  2. **负载因子 α = 元素数 / 桶数 保持在合理范围**。
     α 越大，冲突越多，探测链越长。链地址法的平均查找长度约为 1 + α/2，
     开放寻址法对 α 极其敏感：线性探测在 α → 1 时性能**断崖式崩塌**。
  所以哈希表必须在 α 超过阈值（链地址法常取 0.75，开放寻址常取 0.5）时 **rehash**：
  开一个更大的桶数组，把所有元素重新散列进去。单次 rehash 是 O(n)，
  但和 `vector` 扩容同理，**均摊到每次插入是 O(1)**。
  开放寻址法删除还必须用**墓碑标记**：不能直接把槽位清空，
  否则会截断探测链，让后面本来能通过继续探测找到的元素永远找不到。
- **代码证据**（`05_hash_table.cpp`）：实测不同负载因子下的平均查找耗时与冲突率，
  可以清楚看到 α 从 0.25 涨到 0.9 时查找耗时的上升曲线，
  以及 α 超过 1 之后链地址法的长链。另外会故意构造大量哈希值相同的键，
  展示链地址法退化成 O(n) 的过程。
- **工程建议**：
  - **用 `std::unordered_map` 时，如果提前知道元素数量，先 `reserve`**，
    避免多次 rehash（和 `vector::reserve` 同理）。
  - **自定义类型做键时，必须提供一个好的 `std::hash` 特化**，
    并且 `operator==` 要和哈希保持一致（相等的对象必须有相同的哈希值，
    反之不要求）。哈希写得差，整个哈希表就废了。
  - `std::unordered_map` 的迭代顺序是**未指定的**，而且 rehash 会让所有迭代器失效。
    需要稳定顺序时用 `std::map`，或者把键单独排序后遍历。
  - 哈希表的常数因子和内存开销比 `std::map` 大得多（桶数组 + 每节点一个指针）。
    元素很少时（几十个以内），`std::map` 或直接线性查找可能更快。

### 4.4 BST 退化：为什么 `std::map` 用红黑树

- **错误直觉**：「二叉搜索树查找是 O(log n)，`std::map` 也是 O(log n)，差不多。」
- **正确模型**：普通 BST 的 O(log n) 只在**树大致平衡**时成立。
  它的高度完全由**插入顺序**决定：
  - 随机顺序插入：期望高度约 1.39 log₂n，是 O(log n)；
  - **升序或降序插入**：每次新键都插在当前最右/最左，树直接退化成一条链表，
    高度 = n，查找退化成 O(n)，递归实现还会**栈溢出**。
  自平衡 BST 通过旋转在每次插入删除后维持平衡：
  - **AVL 树**：要求左右子树高度差 ≤ 1，最严格，查找略快（高度更小）；
  - **红黑树**：只要求「最长路径不超过最短路径的 2 倍」，平衡更宽松。
  关键在于**旋转次数**：AVL 的删除可能需要沿路径一路旋转上去，最坏 O(log n) 次旋转；
  而红黑树的插入最多 **2 次**旋转、删除最多 **3 次**旋转就能恢复性质
  （其余情况靠**重新着色**解决，比旋转便宜）。
  `std::map` / `std::set` 是**通用容器**，必须假设插入删除很频繁，
  所以选了「查找略慢一点、但插删成本更低、实现更简单」的红黑树。
  顺带一提，这也是为什么 `std::map` 的迭代器**不会**因为插入删除（除被删元素外）而失效——
  红黑树的重着色和少量旋转不改变其它节点的内存位置。
- **代码证据**（`06_binary_search_tree.cpp`）：有序插入 10 万条数据，
  朴素 BST 的高度退化成约 10 万（等于元素个数），`std::map` 的高度约 30 余
  （红黑树高度上界 2·log₂(n+1) ≈ 34）。查找耗时相差几个数量级。
- **工程建议**：
  - **需要有序容器就用 `std::map` / `std::set`，永远不要手写普通 BST 当容器。**
  - 只需要「插入 + 查询存在性 + 不需要顺序」时，`std::unordered_map` / `std::unordered_set`
    的平均 O(1) 通常更快。
  - 只有一个场景值得考虑手写：**数据全部离线已知、可以一次性构建一棵静态平衡树**
    （例如把有序数组建成完全平衡 BST 用于只读查询），这时不需要维护平衡。
  - 面试里手写 BST 是常见考点，但要说清楚「它在最坏情况下会退化，
    所以生产用红黑树」。**能说出这句话，比写出代码更能体现工程素养。**

### 4.5 `build_heap` 为什么是 O(n) 而不是 O(n log n)

- **错误直觉**：「建堆要对 n 个元素各做一次 `sift_down`，每次 O(log n)，
  所以是 O(n log n)。」
- **正确模型**：这个乘法是**上界放得太松**了，因为它假设**每个节点的高度都是 log n**。
  实际上绝大多数节点都很矮：
  - 高度为 h 的节点最多有 ⌈n / 2^(h+1)⌉ 个（叶子是高度 0，占一半）；
  - 所以总代价 = Σ(h 从 0 到 log n) ⌈n / 2^(h+1)⌉ · O(h)
    = O(n · Σ h/2^(h+1))；
  - 而 Σ(h 从 0 到 ∞) h/2^h = 2 是**收敛常数**，
    所以总和 = O(n · (1/2) · 2) = **O(n)**。
  直觉版本：**从下往上建堆时，越往上的节点数量越少**，
  而「数量指数减少」正好抵消了「高度线性增加」。相反，
  「逐个 `sift_up` 插入建堆」的做法是从上往下、最底层节点要走满 log n 层，
  那个确实是 O(n log n)。
- **代码证据**（`07_heap_and_priority_queue.cpp`）：实测
  「从最后一个非叶节点倒着 `sift_down` 建堆」（O(n)）
  vs 「逐个 `push` 上浮建堆」（O(n log n)）的耗时，后者明显更慢。
- **工程建议**：
  - 已经有一个完整数组要变成堆时，**用 `std::make_heap`（O(n)），
    不要循环 `push`（O(n log n)）**。
  - 只需要前 K 个最大元素时，用「大小为 K 的堆」是 O(n log K)；
    而如果 K 接近 n，**整体 `std::sort` 或 `std::partial_sort` 反而更合适**。
  - 这个推导是「渐进分析要算总账、不能对每层用最坏界」的经典案例，
    面试常考，务必能自己推一遍。

### 4.6 快排的最坏情况与随机化

- **错误直觉**：「快排平均 O(n log n)，所以随便选 pivot 都行。」
- **正确模型**：快排的性能**完全取决于划分是否均衡**。
  如果每次划分都只能把区间分成 1 和 n-1 两部分，递归深度就是 n，
  总代价 n + (n-1) + ... + 1 = **O(n²)**。
  而「固定取首元素（或末元素）作为 pivot」在**已经有序的输入上恰好必然触发这个最坏情况**——
  而现实中「已经有序」或「近乎有序」的数据非常常见（日志按时间写入、数据库主键递增）。
  解决办法：
  - **随机化**：随机选 pivot。这样对手无法构造出针对你的输入，
    期望复杂度是 O(n log n)，且几乎不可能持续命中坏运气；
  - **三数取中**：取首、中、尾三个元素的中位数作 pivot，
    对「已排序」和「近乎有序」输入效果极好，且比随机化开销更小（不用调用随机数发生器）。
  另外两个工程要点：
  - **尾递归优化**：先递归**较小**的一侧，用循环处理**较大**的一侧。
    这样递归深度被压到 O(log n)，避免最坏情况下的栈溢出。
  - **小数组切换插入排序**：区间小到 16 个元素左右时，直接插入排序更快，
    因为快排的递归和划分开销在小规模下不划算。这正是「introsort」的做法之一。
  最后，**introsort**（`std::sort` 的实现）还加了一道保险：
  当递归深度超过 2·log₂n 时，直接切换到**堆排序**，
  从而在保留快排平均性能的同时，把最坏情况**保证**在 O(n log n)。
- **代码证据**（`08_sorting_algorithms.cpp`）：对**已排序数组**，
  「固定取首元素」的快排退化到 O(n²)（在几千个元素上就能看出明显差距），
  而随机化 / 三数取中版本保持 O(n log n)。
- **工程建议**：
  - **永远不要自己写快排上线**，用 `std::sort`。它已经做了随机化/三数取中、
    小区间插入排序、深度超限切堆排这三件事，而且经过了几十年的实战调优。
  - 如果面试要你手写快排，**主动说出这三条优化**，尤其是「尾递归优化把栈深度压到 O(log n)」，
    这是区分「背过代码」和「真懂」的分水岭。
  - 需要**保证**最坏 O(n log n) 且不稳定排序时用 `std::sort`；
    需要稳定时用 `std::stable_sort`；需要原地 + O(1) 空间 + 保证最坏时考虑 `std::partial_sort` / 堆排序。

### 4.7 排序稳定性什么时候真的重要

- **错误直觉**：「稳定性是教科书概念，实际写代码用不到。」
- **正确模型**：稳定 = **相等元素的相对顺序在排序后保持不变**。
  它只在「元素有多个字段、你按其中一个字段排序、且另一个字段的顺序有意义」时才起作用。
  典型场景：
  - **多级排序**：先按「部门」排，再按「工资」排。如果第二次排序是稳定的，
    那么同一部门内的工资顺序就会保留第一次排好的部门顺序，
    于是你**用两次稳定排序实现了多关键字排序**（从最后一个关键字往前排）。
    如果第二次不稳定，第一次的成果就被打乱了。
  - **增量刷新 / 分页**：列表先按时间排，用户点击「按名称排序」后，
    希望同名项的原有时间顺序仍然保留，避免界面「跳动」。
  - **日志 / 流水**：同一时刻的记录要保持写入顺序。
  哪些算法稳定：冒泡、插入、归并、计数（倒序填充时）稳定；
  选择、希尔、快排、堆排**不稳定**。
  注意「选择排序不稳定」的原因很有教育意义：它会把最小元素和首位**远距离交换**，
  一下子跨过很多相等元素，打乱它们的相对顺序。
- **代码证据**（`08_sorting_algorithms.cpp`）：用「键相同但带唯一 id」的结构体排序，
  检查相同键的相对顺序是否保持，给出可运行的稳定性证据。
  同时会打印一张完整的稳定性对照表。
- **工程建议**：
  - 需要稳定时，**用 `std::stable_sort`**，不要自己「加一个序号字段再比较」——
    虽然那个技巧有效（把比较器写成「先比主键、相等则比原始下标」），
    但它需要额外的存储和一次额外的比较，`std::stable_sort` 更直接。
  - `std::sort` 是**不稳定**的。如果你的代码依赖相等元素的顺序，这是个隐蔽的 bug，
    在数据量变化、实现变化（不同 STL 版本）时才会暴露，极难排查。
  - 多关键字排序时，记住「**从最后一个关键字往前依次稳定排序**」这个套路。

### 4.8 DP 的遍历顺序：0-1 背包倒序 vs 完全背包正序

这是动态规划里**最经典、最容易错、面试最爱问**的一个点。

- **错误直觉**：「一维滚动数组优化就是把二维的 `dp[i][j]` 写成 `dp[j]`，
  里面那层循环正着写倒着写都一样。」
- **正确模型**：**遍历顺序直接决定语义**。
  先看二维的 0-1 背包转移方程：
  `dp[i][j] = max(dp[i-1][j], dp[i-1][j - w[i]] + v[i])`
  （注意两项都来自 `i-1`，也就是「只用前 i-1 件物品」的状态）。
  压成一维时，我们希望 `dp[j - w[i]]` 读到的是**上一轮 i-1 的旧值**。
  - **0-1 背包必须倒序遍历 j**（从大到小）：这样 `dp[j-w]` 因为下标更小、
    **还没被本轮更新过**，读到的正是旧值，符合「每件物品只能用一次」。
  - 如果正序遍历 j：`dp[j-w]` 已经被本轮 i 更新过了，
    相当于「第 i 件物品可以被重复放入」，**那就变成了完全背包**。
  反过来看完全背包，它的转移方程本来就允许重复使用：
  `dp[i][j] = max(dp[i-1][j], dp[i][j - w[i]] + v[i])`
  （第二项是 `i` 而不是 `i-1`，表示「已经考虑过放第 i 件，还可以再放」），
  所以压成一维后**正序遍历**正好对应这个语义。
  **一句话记法：0-1 背包倒序（怕重复用），完全背包正序（就是要重复用）。**
- **代码证据**（`10_dynamic_programming.cpp`）：故意把 0-1 背包写成正序，
  打印出它与正确答案的差异，用可运行的错误结果证明这个坑是真的。
- **工程建议**：
  - 写背包类 DP 时，**先把二维方程写出来，再决定一维的遍历方向**，
    不要凭记忆写。记忆容易错，方程不会骗你。
  - 判断方法很简单：问自己「`dp[j-w]` 应该是**本轮**的值还是**上一轮**的值？」
    上一轮 → 倒序；本轮 → 正序。
  - 同理，**求方案数的零钱兑换**必须**外层遍历硬币、内层遍历金额**，
    否则会重复计数（把 {1,2} 和 {2,1} 当成两种方案）。
    这也是「遍历顺序决定语义」的另一个实例。

### 4.9 Dijkstra 为什么不能处理负权边

- **错误直觉**：「Dijkstra 每次取当前距离最小的点，肯定是对的，
  负权边无非是让某些距离更小，应该也能算吧。」
- **正确模型**：Dijkstra 的正确性建立在一条**贪心前提**上：
  **「当我把一个点从优先队列里取出来（定型）时，它到源点的距离已经是最终最短距离。」**
  为什么这个前提在非负权下成立？因为从源点出发到任何未定型点的路径，
  长度只会**单调不减**地增长——所有边的权重都 ≥ 0，
  所以「绕道经过其他未定点」不可能得到一个更短的距离。
  一旦出现负权边，这个单调性就被破坏了：
  从已定型的点出发，经过一条负权边，可能到达一个距离**更小**的点。
  但 Dijkstra 已经把那个点定型、不会再看它第二眼，于是结果是**错的**。
  反过来说，负权边也意味着「**最短路可能包含环**」（绕一圈反而更短），
  这时连「最短路径」这个概念都需要重新定义（只有不存在负环时才良定义）。
  所以要处理负权就得用 **Bellman-Ford**：它不假设任何点已经定型，
  而是**反复对所有边做松弛**，最多迭代 V-1 轮
  （因为一条最短路径最多包含 V-1 条边，没有负环时）。
  代价是 O(V·E)，比 Dijkstra 的 O((V+E) log V) 慢。
  Bellman-Ford 还有一个 Dijkstra 给不了的能力：**检测负环**——
  如果在第 V 轮还能松弛成功，就说明存在负环（可以无限绕圈让距离趋于负无穷）。
  补充：如果图里**没有负环**，可以用 **SPFA**（Bellman-Ford 的队列优化版）
  或 **Johnson 算法**（先用 Bellman-Ford 重赋权把所有边变成非负，
  再对每个点跑一次 Dijkstra）来加速。
- **代码证据**（`09_graph_algorithms.cpp`）：构造一个**具体的反例图**，
  分别跑 Dijkstra 和 Bellman-Ford，打印两者结果并展示 Dijkstra 给出的错误距离。
  同时在一个含负环的图上演示 Bellman-Ford 检测出负环。
- **工程建议**：
  - 选最短路算法前，**先确认边权的符号**。这是需求层面的问题，不是实现层面的。
  - 无权图（或权值全相同）→ **BFS**，O(V+E)，比 Dijkstra 快得多，别过度设计。
  - 非负权 → **Dijkstra + 优先队列**。
  - 有负权 → **Bellman-Ford**（并检查负环）；V 很小而要求全源 → **Floyd-Warshall**。
  - 注意 Dijkstra 的堆实现里那个 `if (d > dist[u]) continue;`——
    这是**惰性删除**技巧：同一个点可能被多次压入堆（每次距离更新都压一次），
    出堆时如果发现这个距离已经不是最新的，就跳过。这样就不需要「修改堆中元素」这个
    `std::priority_queue` 不支持的操做了。

## 5. 算法题的实用解题框架

做题的第一步不是写代码，而是**从题目特征反推该用什么工具**。
下面这张表是本章最实用的部分，建议当成查表用。

### 5.1 「看到什么 → 想到什么」

| 题目里看到这些字眼 | 立刻想到 | 复杂度 |
| --- | --- | --- |
| 求第 K 大 / 第 K 小、Top-K | **大小为 K 的堆** 或 **`std::nth_element`** | O(n log K) / 平均 O(n) |
| 前 K 个高频元素 | 哈希表计数 + 大小为 K 的堆 | O(n log K) |
| 最短路，**边权都相同 / 无权** | **BFS** | O(V+E) |
| 最短路，边权**非负** | **Dijkstra + `priority_queue`** | O((V+E) log V) |
| 最短路，**有负权** | **Bellman-Ford** / SPFA；有负环要注意 | O(V·E) |
| 最短路，**多源 / 全源**，V 小 | **Floyd-Warshall** | O(V³) |
| 依赖关系、课程表、编译顺序、任务调度 | **拓扑排序**（Kahn 入度法） | O(V+E) |
| 连通性、朋友圈、岛屿合并、动态连通 | **并查集**（路径压缩 + 按秩合并） | 近 O(1) |
| 最小代价连通所有点 / 铺路 / 铺网线 | **最小生成树**（Kruskal 或 Prim） | O(E log E) / O(E log V) |
| 括号匹配、嵌套结构、表达式求值 | **栈** | O(n) |
| 单调栈、下一个更大元素、柱状图最大矩形 | **单调栈** | O(n) |
| 滑动窗口最大值 / 最小值 | **单调队列（`std::deque`）** | O(n) |
| 按层遍历、层序、最短步数（每步代价相同） | **BFS + 队列** | O(V+E) |
| 回退、撤销、路径记录、全排列 | **栈 / 递归回溯** | 指数级 |
| 子数组和 / 区间和，**多次查询** | **前缀和** | 预处理 O(n)，查询 O(1) |
| 子数组积 / 区间积，且元素非零 | **前缀积**（注意零的处理） | 同上 |
| 区间加、区间求和，多次操作 | **差分数组** / 树状数组 / 线段树 | O(1) 修改或 O(log n) |
| 区间合并、会议安排、插入区间 | **按起点排序后扫描** | O(n log n) |
| 求「最长 / 最短 / 最大 / 最小」且**有阶段决策** | **动态规划** | 看状态维度 |
| 有「选或不选」「用前 i 个」「容量限制」 | **背包类 DP** | O(n·W) |
| 两个字符串的比较 / 匹配 / 编辑 | **二维 DP（LCS / 编辑距离）** | O(n·m) |
| 最长递增子序列 | **O(n log n) 贪心 + 二分**（维护 tails） | O(n log n) |
| 求方案数、能不能凑出来 | **DP（完全背包类）**，注意遍历顺序 | O(n·W) |
| 每次都能证明「局部最优 = 全局最优」 | **贪心** | 通常 O(n log n) |
| 需要枚举所有可能 + 剪枝 | **回溯** | 指数级 |
| 二分查找、单调性、求最小可行值 | **二分答案** | O(n log(range)) |
| 数据流中位数 | **双堆**（大顶堆 + 小顶堆） | 插入 O(log n)，查询 O(1) |
| 合并 K 个有序序列 | **优先队列 K 路归并** | O(N log K) |
| 判断环（链表） | **Floyd 快慢指针** | O(n)，O(1) 空间 |
| 判断环（有向图） | **拓扑排序 / DFS 三色标记** | O(V+E) |
| 去重 + 需要有序 | **`std::set` / `std::map`** | O(log n) / 次 |
| 去重 + 不需要有序，只要判存在 | **`std::unordered_set`** | 平均 O(1) / 次 |
| 计数、词频、分组 | **`std::unordered_map`** | 平均 O(1) / 次 |

### 5.2 一个可复用的解题流程

1. **先手算小样例**。用 3 到 5 个元素的例子把题目走一遍，
   搞清楚「输入 → 输出」的映射到底在算什么。这一步能避免 80% 的方向性错误。
2. **写下暴力解法，并说清复杂度**。暴力解法是最好的正确性参照物，
   后面写优化版本时可以拿它对拍。
3. **问三个问题，决定用哪个范式**：
   - 有**最优子结构**吗（大问题的最优解能由小问题的最优解拼出来）？
   - 有**重叠子问题**吗（递归会重复算同一件事）？
   - 有**无后效性**吗（一旦确定当前状态，后面的决策不受更早历史的影响）？
     三个都是「是」→ 动态规划。
   - 子问题**不重叠** → 分治。
   - 能证明局部最优即全局最优 → 贪心。
   - 只是「在集合里找」或「按层扩散」 → 哈希表 / BFS / 排序后扫描。
4. **估算数据规模，验证可行性**。
   用「每秒约 10⁸ 次基本操作」做粗略标定（面试语境下常用 10⁷ 到 10⁸）：

   | n 的规模 | 可接受的复杂度 |
   | --- | --- |
   | n ≤ 10 | O(n!)、O(2ⁿ) |
   | n ≤ 20 | O(2ⁿ) |
   | n ≤ 500 | O(n³) |
   | n ≤ 5000 | O(n²) |
   | n ≤ 10⁶ | O(n log n) |
   | n ≤ 10⁸ | O(n) |
   | n > 10⁸ | O(log n)、O(1) |

   这一条极其实用：**看到 n ≤ 20 就该想状压或暴力枚举，
   看到 n ≤ 5000 就该想 O(n²) DP，看到 n = 10⁵ 到 10⁶ 就只能 O(n log n) 或 O(n) 了。**
5. **写出优化的解法，用暴力解法对拍**。本章每个 `.cpp` 都在做这件事，
   这是保证自己代码正确的最高效方式。
6. **检查边界**：空输入、单元素、全相同、已排序、逆序、溢出（`int` 不够就用 `long long`）。

### 5.3 复杂度估算速记

- 「n 每翻倍，耗时怎么变」是判断复杂度的最快方法：
  约 1 倍 → O(1) / O(log n)；约 2 倍 → O(n)；约 2.1 倍 → O(n log n)；约 4 倍 → O(n²)。
  （本章 `01_complexity_and_measurement.cpp` 实测得到的就是这几个数。）
- 递归的复杂度看**递推式**：主定理记不住也没关系，
  把递归树画出来、数一数每层的工作量和层数，通常就够了。
- 别忘了算**空间**：递归的栈深度也是空间，而且它是**最容易导致程序崩溃**的那部分
  （`06` 里的朴素 BST 递归在退化树上会爆栈，`09` 里的大图递归 DFS 同理）。

## 6. 实用开发习惯

### 6.1 为什么生产代码不该手写红黑树 / 快排

不是因为「你写不出来」，而是因为**收益远远不抵成本**：

1. **正确性成本**：`std::map` 的红黑树、`std::sort` 的 introsort，
   是被全世界用了二三十年、在无数输入分布和平台上验证过的。
   你手写的版本要覆盖同样多的边界情况（删除时的双黑修正、
   快排遇到全相同元素、比较器抛异常时的强保证……），
   测试成本高得离谱，而且**漏掉一个分支就是一个隐蔽的线上 bug**。
2. **性能成本**：`std::sort` 至少做了这三件事，你很难同时做到：
   - **比较器内联**：比较操作被内联进排序循环，消除函数调用开销，
     内联后编译器还能把比较结果用于分支预测；
   - **内存局部性**：循环的写法对缓存和预取器友好；
   - **混合策略**：小区间切插入排序、深度超限切堆排序，兼顾平均性能与最坏保证。
3. **维护成本**：下一个读代码的人不知道你的实现有什么隐含假设。
   而 `std::sort` 的行为是**有标准文档和复杂度承诺**的。

**结论：能用 STL 就用 STL。你的价值在于「选对数据结构和算法」，
不在于「手写一个更慢的排序」。**

### 6.2 什么时候真的需要自己实现

不是「永远不要手写」，而是「**手写要有明确理由**」。合理的理由包括：

1. **STL 里根本没有**：并查集、图算法、线段树、树状数组、跳表、
   单调队列、各种领域专用结构。这些必须自己写（或者用成熟第三方库，
   如 Boost.Graph、abseil）。
2. **有特殊的内存约束**：
   - 嵌入式 / 实时系统：不允许动态分配，必须用**静态数组 + 容量上限**的容器，
     并且要能给出**最坏执行时间的上界**。
   - 内存池 / 竞技场分配（arena）：为了把成千上万个小对象放在一起，
     提升缓存局部性并消除逐个 `free` 的开销。
   - 共享内存 / 内存映射文件：不能有指针，必须用**偏移量**代替指针
     （因为不同进程映射到不同地址）。
3. **STL 的复杂度不满足要求**：例如需要 O(1) 最坏（不是均摊）的插入，
   而 `std::vector` 的 `push_back` 是均摊 O(1)；
   或者需要「可持久化」（persistent）结构，STL 完全没有。
4. **有特殊的数据布局要求**：结构体数组（SoA）而不是数组结构体（AoS），
   为了 SIMD 向量化或 GPU 上传；或者需要严格控制 padding 和 `sizeof`。
5. **避免异常 / RTTI**：某些嵌入式或游戏主机环境禁用异常，
   而 STL 容器在分配失败时的行为和异常强相关。
6. **教学 / 学习目的**：就像本章——目的是理解，不是替代。

**关键判断标准**：如果你不能用一句话说清「为什么 STL 不行」，
那就用 STL。

### 6.3 怎么用 `assert` + 对拍保证自写算法正确

这是本章每个 `.cpp` 都在用的方法，也是最高效的验证手段：

1. **准备一个「笨但对」的参照实现**。暴力枚举、或者 STL 的等价物
   （`std::sort`、`std::map`、`std::unordered_map`）。它慢没关系，它必须简单到你能一眼看出是对的。
2. **`assert` 对拍**：
   ```cpp
   assert(MySort(v) == SortedCopy(v));   // 逐元素相等
   assert(MyMap.Size() == RefMap.size());
   ```
3. **`assert` 只能告诉你「错了」，不能告诉你「哪里错了」**。
   所以对拍失败时，要打印最小的失败用例：
   - 用**小规模随机测试**（n = 1 到 20，值域 0 到 5，故意制造大量重复）
     跑几千轮，比一个大用例更容易定位问题；
   - 一旦失败就打印输入，然后把这个输入固化成回归测试。
4. **覆盖这些「坏输入」**：空、单元素、全相同、已排序、逆序、
   大量重复、以及**极值**（最小/最大整数，用于发现溢出和边界比较写错，
   比如把 `<` 写成 `<=`）。
5. **`assert` 在 Release（`NDEBUG`）下会被去掉**，
   所以它只适合做开发期验证，**不能用来做运行时参数校验**。
   需要永远生效的检查要用显式的 `if` + 抛异常或返回错误码。
6. **善用工具**：MSVC 的 `/fsanitize=address`（ASan）、
   `/RTC1`（运行时检查）、`_CRTDBG_MAP_ALLOC`（内存泄漏检测）
   能自动发现越界、use-after-free、泄漏。手写容器时至少跑一遍 ASan。

### 6.4 性能优化的正确顺序

**绝大多数性能问题都出在「选错了算法或数据结构」，而不是「代码写得不够妙」。**

正确的顺序是：

1. **先测量，找出真正的热点**。
   不要猜。用性能分析器（Visual Studio 的 Performance Profiler、
   `perf`、`VTune`），或者至少用 `std::chrono` 在关键路径上打点。
   人的直觉在性能上非常不可靠——本章 4.2 节的数据就是证据：
   很多人「觉得」链表快，实测慢 20 倍。
2. **先优化算法和数据结构**（换掉 O(n²) → O(n log n)，换掉链表 → `vector`，
   加一个哈希表把 O(n) 查找降到 O(1)）。
   这一步通常能带来**一个数量级**的提升，而且代码往往更简单。
3. **然后优化内存访问模式**：
   - 提高**缓存局部性**（连续访问、SoA 布局、把热数据聚在一起）；
   - 减少**分配次数**（`reserve`、对象池、批量分配）；
   - 消除**指针追逐**（用索引代替指针，用数组代替链表）。
   这一步通常能再带来 2 到 10 倍。
4. **最后才做微优化**：手动内联、循环展开、
   用位运算代替分支、`[[likely]]` 提示分支预测。
   这一步通常只带来百分之几十。
5. **不要过早优化（premature optimization）**：
   - 为了「可能更快」而牺牲可读性，通常得不偿失；
   - 优化前先有**基准测试（benchmark）**，优化后能证明它确实变快了；
   - 优化后**必须重新跑正确性测试**——优化是引入 bug 的高发区。
6. **注意 Debug 和 Release 的差异**：
   本章所有数字都是 Debug 的。Debug 下 STL 有大量检查、
   没有内联、没有优化，**不能代表线上性能**。
   做任何真实的性能结论，都必须在 **Release（`/O2`）** 下重测。
   （本章的结论「用 STL」在 Release 下只会更成立，
   因为优化器对内联和向量化的收益更大。）

## 7. 刷题与面试准备建议

以下针对「软件开发方向」的求职者。

### 7.1 高频考点排序

按「出现频率 × 性价比」排序，建议按这个顺序投入时间：

1. **数组 / 字符串 + 双指针 / 滑动窗口 / 前缀和**（最高频，最容易拿分）
2. **哈希表**（`unordered_map` 计数、去重、找补数）
3. **二分查找**（包括「二分答案」这个变体，区分度很高）
4. **栈与队列**（括号匹配、单调栈、单调队列）
5. **链表**（反转、快慢指针、合并、判环）——操作简单但**最容易写出指针 bug**，
   写的时候一定要画图，注意头节点和空链表的处理（用哨兵节点能省一半的边界判断）
6. **二叉树**（三种遍历的递归与迭代、层序、最近公共祖先、验证 BST）
7. **动态规划**（背包、LCS / 编辑距离、LIS、打家劫舍、股票系列）——
   **投入产出比最高也最需要练**，因为套路有限而变体极多
8. **堆 / Top-K**（第 K 大、数据流中位数、合并 K 路）
9. **图**（BFS / DFS、拓扑排序、并查集；Dijkstra 在面试里出现频率中等）
10. **回溯 / 递归**（全排列、子集、组合总和、N 皇后）
11. **排序**（手写快排 / 归并，以及「用排序预处理」的各种变形）
12. **位运算**（出现频率低，但题目往往很短）

**注意**：本章讲的「手写红黑树」「手写哈希表」在面试里通常**不会**要求完整实现，
但会问「它的复杂度是多少」「为什么这么设计」。
所以重点是**理解原理并能说清取舍**，而不是背代码。

### 7.2 怎么写题解笔记

有效的题解笔记不是「贴一份 AC 代码」，而是包含这五块：

1. **一句话概括题目**（用你自己的话，不看原题说清楚）。
2. **思路是怎么想到的**：从题目里哪个**关键词**触发了我用这个数据结构/算法？
   这一步最重要——它积累的是**识别能力**，也就是本章第 5 节那张表。
3. **复杂度分析**：时间、空间，都要写，并且说清是怎么算出来的。
   面试里这一步是必问项。
4. **易错点 / 边界**：这次为什么错了？哪个边界没想到？
   （例如「`int` 溢出」「忘记处理空输入」「二分边界写错导致死循环」。
   把这些单独记一个『坑清单』，复习时只看这个。）
5. **可对比的其他解法**：暴力解、优化解、以及「如果用另一种数据结构会怎样」。
   有对比才有取舍，有取舍才是工程思维。

**建议的笔记组织方式**：按**题型/套路**分类，而不是按刷题日期。
同一类的题目放在一起，你会很快发现「这一类题的模板其实就一个」。

### 7.3 复杂度必须能说出来

这是面试的**硬性要求**，说错基本会被扣分：

- 写完代码，**不等面试官问，主动说出**时间和空间复杂度。
- 说复杂度时要说清**变量指什么**：是「n 是字符串长度」还是
  「n 是元素个数、m 是元素最大长度」？二维 DP 要说清是 O(n·m) 还是 O(n·W)。
- 要能解释**为什么**是这个复杂度，而不是背结论。
  例如「快排平均 O(n log n) 是因为平均划分深度是 O(log n)，
  每层工作 O(n)」——能推导比能背更有说服力。
- **主动提到最坏情况**。例如：
  「哈希表平均 O(1)，最坏 O(n)；`std::sort` 保证 O(n log n)（introsort）；
  快排最坏 O(n²)，所以生产用 `std::sort`。」
  这种回答能立刻把「背过书」和「做过工程」区分开。
- 也要能说出**空间**的隐藏成本：
  「递归版的空间是 O(h) 的栈深度，h 是树高；退化时会到 O(n)，有爆栈风险，
  所以我改成迭代了。」——这一句能体现真实的工程经验。

### 7.4 面试中的加分项

- 写完解法后**主动**给出「如果数据规模变大 / 有内存限制 / 数据有序，
  我的解法要怎么调整」。
- 主动提出**测试用例**：「我会测空输入、单元素、全相同、已排序、以及极值。」
- 提到**具体用哪个 STL 容器以及为什么**：
  「这里用 `unordered_map` 而不是 `map`，因为不需要有序遍历，要的是平均 O(1)。」
- 如果题目有多个解法，**先说出复杂度谱系**（暴力 → 优化 → 最优），
  再实现其中一个，并说明取舍。

## 8. 自测题（10 道，含答案）

### 题 1
`std::vector<int>` 的 `push_back` 是「均摊 O(1)」，但某一次 `push_back` 的实际代价是 O(n)。
这两句话矛盾吗？请解释，并说明为什么不能因为「怕扩容」而改用 `std::list`。

<details>
<summary>答案</summary>

**不矛盾。** 均摊分析允许单次操作很贵，只要这种「贵」出现得足够稀疏。

设增长因子为 k，一次扩容把容量从 c 变成 k·c，需要搬移 c 个元素。
在插入 n 个元素的过程中，扩容发生在容量为 1, k, k², ... 时，
所以总搬移次数是 `1 + k + k² + ... + n/k ≈ n·k/(k-1)`：
k = 2 时是 2n，k = 1.5 时是 3n。**总量是 O(n)**，
摊到 n 次 `push_back` 上，每次就是 O(1)。

直觉版本：越是贵的扩容，发生的间隔越长，所以贵的那几次被大量便宜操作摊薄了。

不能改用 `std::list` 的原因：
1. 扩容成本已经被摊薄，而链表的遍历代价（缓存不友好）是**每一次访问**都在付。
   本章实测：遍历求和 20 万个 `int`，`vector` 306 微秒，`list` 6229 微秒，**慢约 20 倍**。
2. 链表每个节点多背 2 个指针，内存开销和 cache line 占用都更高。
3. 链表不支持随机访问。

**结论**：用 `vector`，并且能预估大小时先 `reserve`。
</details>

### 题 2
为什么 `std::vector` 在 MSVC 上用 1.5 倍增长，而 GCC 用 2 倍？
「2 倍增长会导致内存无法复用」是什么意思？

<details>
<summary>答案</summary>

关键在于**释放掉的老内存块能不能被后续的新分配复用**。

假设增长因子是 2，容量序列是 1, 2, 4, 8, 16, ...。
当需要从容量 16 扩到 32 时，老块是 16，新块是 32——
**新块比之前所有老块加起来（1+2+4+8+16 = 31）还大**。
即使之前所有老块都已经被释放、并且内存分配器把它们合并成了一整块连续空间（31 个单位），
也**装不下**这个 32 单位的新块。所以每次扩容都只能向系统申请全新的内存，
老内存永远无法被这次增长复用。结果是：内存占用峰值高，而且容易产生碎片。

换成 1.5 倍：容量序列是 1, 2, 3, 4, 6, 9, 13, 19, ...。
从容量 13 扩到 19 时，新块 19；而之前释放的老块
1+2+3+4+6+9+13 = 38 > 19，**足以容纳新块**。
所以分配器有机会在原有区域里就地复用空间，减少向系统申请内存的次数，
降低峰值占用和碎片。

**代价**：1.5 倍增长意味着扩容更频繁（同样的 n 需要更多次 rehash/搬移），
总搬移量上界从 2n 变成 3n，常数更大、内存利用率稍低。
这是「内存复用」和「搬移次数」之间的取舍。

（顺带一提：本章实测 MSVC 的容量序列正是 `1 2 3 4 6 9 13 19 ...`，
累计搬移 414776 ≈ 2.07n 次，与 3n 的上界吻合。）
</details>

### 题 3
既然链表「在已知位置插入删除是 O(1)」，为什么实际项目中几乎不用 `std::list`？
请从**三个不同角度**回答。

<details>
<summary>答案</summary>

**角度一：找到那个「已知位置」本身通常要 O(n)。**
「已知位置」在代码里表现为「已经持有指向该节点的迭代器」。
但如果你是从值出发找位置（`std::find`），那一步就是 O(n)，
插入的 O(1) 被寻找的 O(n) 完全淹没，总代价和 `vector` 一样是 O(n)。
而且 `vector` 的 O(n) 搬移是**连续内存的 memmove**，非常快；
链表的 O(n) 查找是**指针追逐**，非常慢。

**角度二：缓存局部性（最致命）。**
CPU 按 64 字节的 cache line 取数据。`vector` 的元素连续，
一条 cache line 装 16 个 `int`，16 次访问只付 1 次内存延迟，
而且硬件预取器能识别顺序访问模式、提前把数据拉进缓存。
链表节点散落在堆上，每走一步都可能 cache miss（几百个 CPU 周期），
且预取器对指针追逐完全无效（下一个地址要读出当前节点才知道）。
实测：同样遍历求和 20 万个 `int`，`vector` 306 微秒，`list` 6229 微秒，慢约 20 倍。

**角度三：内存开销。**
每个 `list` 节点要额外存前驱和后继两个指针（64 位下 16 字节），
再加上分配器的头部开销和对齐填充。存 4 字节的 `int` 却要付出 20 字节以上的代价，
内存放大 5 倍以上。同样的数据占用更多 cache line，进一步恶化角度二的问题。
（本章实测 `sizeof(std::list<int>)` = 24 字节，节点约 20 字节。）

**补充**：链表还有一个隐性缺点——每个节点一次独立的 `new`，
分配/释放开销大，容易造成堆碎片；而 `vector` 一次分配一大块。

**所以**：需要频繁中间插入删除时，先考虑 `std::deque`（两端均摊 O(1)、分块连续），
真正需要链表语义时再考虑 `std::list`，并且**一定要先测**。
</details>

### 题 4
开放寻址哈希表删除一个元素时，为什么不能直接把槽位置空？
墓碑（tombstone）标记解决了什么问题，它又带来了什么新问题？

<details>
<summary>答案</summary>

**为什么不能直接置空**：开放寻址的查找依赖**探测链**——
从 `hash(key)` 开始的槽位序列。查找时一旦遇到空槽就**停止**，判定「不存在」。

假设插入顺序造成如下布局（线性探测，容量 7，`hash` 值都是 0）：
槽位 0 是 A，槽位 1 是 B，槽位 2 是 C。
现在查找 C：从槽位 0 开始，0 是 A（不匹配）→ 1 是 B（不匹配）→ 2 是 C，找到。

如果把 B 直接删掉、槽位 1 置空，再查找 C：
从槽位 0 开始 → 1 是空槽 → **立即判定「C 不存在」**——错了！
B 的删除**截断了探测链**，导致它后面本应被找到的元素永远找不到。

**墓碑的作用**：删除时把槽位标记为「已删除」（墓碑），而不是空。
查找时遇到墓碑会**继续探测**（不停止），遇到真正的空槽才停止。
插入时可以把新元素放进墓碑槽位，从而复用空间。

**墓碑带来的新问题**：
1. **空间浪费与性能退化**：墓碑会不断累积，表里可用的「真空槽」越来越少，
   探测链越走越长，查找性能持续下降，即使实际元素个数并不多。
   极端情况下（大量插入删除交替）表里全是墓碑，查找退化成 O(n)。
2. **`size` 语义要小心**：墓碑不计入元素个数，但占用槽位，
   所以负载因子的计算要考虑「元素数 + 墓碑数」，否则会误判。
3. **必须定期清理**：需要在「墓碑比例超过阈值」时触发 **rehash**，
   把所有有效元素重新散列到新表里，丢弃所有墓碑。
   这是开放寻址法必须付出的维护成本。

**对比**：链地址法删除就简单得多——直接从链表里摘掉节点即可，
没有探测链被截断的问题，也不需要墓碑。这是链地址法的一个实际优势。
</details>

### 题 5
按升序（1, 2, 3, ...）往一棵朴素 BST 里插入 10 万个元素，
树高是多少？查找一个不存在的元素的比较次数是多少？
`std::map` 做同样的事，高度大约是多少？从**旋转次数**的角度说明
`std::map` 为什么选红黑树而不是 AVL 树。

<details>
<summary>答案</summary>

**朴素 BST**：按升序插入时，每个新键都比之前所有键大，
所以每次都插在**当前最右节点的右孩子**位置，树退化成一条**只有右孩子的链**。
- 树高 = 10 万 - 1（如果根高度记为 0），也就是 **O(n)**。
- 查找一个不存在的元素（比如比所有元素都大）需要一直向右走到底，
  比较 **10 万次**，复杂度 **O(n)**，和链表查找一模一样。
- 更危险的是：如果插入/查找/删除用**递归**实现，
  递归深度就是 10 万层，**几乎必然栈溢出崩溃**。
  这是很真实的工程坑，所以本章的高度统计和查找都用迭代实现。

**`std::map`（红黑树）**：红黑树保证最长路径不超过最短路径的 2 倍，
高度上界是 `2·log₂(n+1)`。n = 10 万时 `log₂(100001) ≈ 16.6`，
所以高度上界约 **34 层**，实测大约在 30 上下。
查找最多比较约 34 次。

**为什么选红黑树而不是 AVL**：
两种都是自平衡 BST，差别在**平衡的严格程度**和**维护平衡的成本**：
- **AVL 树**要求任意节点左右子树高度差 ≤ 1，平衡最严格，
  所以**树高更小、查找更快**（这个优势很小，只差一个常数因子）。
  但代价是插入删除后**更容易失衡**，需要沿路径一路向上修正，
  删除时最坏可能要做 **O(log n) 次旋转**。
- **红黑树**只要求「最长路径 ≤ 2 × 最短路径」，这是一个**更宽松**的平衡条件。
  它通过**重新着色**（改一个 bit，非常便宜）来处理大部分情况，
  只在必要时旋转：**插入最多 2 次旋转，删除最多 3 次旋转**。

`std::map` / `std::set` 是**通用容器**，设计时必须假设
「插入和删除可能和查找一样频繁」。在这种假设下，
**红黑树用「查找慢一点点」换来了「插删成本低很多」**，整体更划算，
而且实现更简单、常数更小。

**如果场景是「几乎只读、极少修改」**，AVL 会更合适——但那种场景下
通常直接用「有序数组 + 二分查找」更好。这也解释了为什么标准库不给 AVL。

**工程结论**：需要有序容器就用 `std::map` / `std::set`，
需要「只要存在性、不要顺序」就用 `std::unordered_map` / `std::unordered_set`。
**永远不要手写普通 BST 当生产容器。**
</details>

### 题 6
证明「从最后一个非叶节点倒着做 `sift_down`」的建堆是 O(n)，
并说明为什么「逐个插入并 `sift_up`」是 O(n log n)。

<details>
<summary>答案</summary>

**核心：`sift_down` 的代价和节点的高度成正比，而高节点非常少。**

考虑一棵有 n 个节点的完全二叉树（堆就是完全二叉树），高度为 h 的层：
- 叶子节点高度为 0，大约占 **n/2** 个；
- 高度为 1 的节点约 **n/4** 个；
- 高度为 2 的约 **n/8** 个；
- 一般地，**高度为 h 的节点最多有 ⌈n / 2^(h+1)⌉ 个**。

每个高度为 h 的节点做 `sift_down` 最多下沉 h 层，代价 O(h)。
所以总代价：

```
T(n) = Σ(h=0 到 log n)  ⌈n / 2^(h+1)⌉ · O(h)
     = O( n · Σ(h=0 到 log n) h / 2^(h+1) )
     = O( n · (1/2) · Σ(h=0 到 ∞) h / 2^h )
```

而 `Σ(h=0 到 ∞) h/2^h = 2` 是一个**收敛的常数**（可用
`Σ h·x^h = x/(1-x)²`，代入 x = 1/2 得 2 验证）。
所以：

```
T(n) = O(n · (1/2) · 2) = O(n)
```

**直觉版本**：建堆是**从下往上**做的，越靠下的层节点越多但越矮，
越靠上的层节点越少但越高。**「节点数量按 2 的幂指数减少」正好抵消了「高度线性增加」**，
求和收敛到一个常数，所以是 O(n)。

**为什么 `sift_up` 建堆是 O(n log n)**：
逐个插入时，第 i 个元素插在**最底层**（叶子位置），
然后 `sift_up` 往上冒泡。最坏情况下它要走到根，代价 O(log n)。
而**几乎每个元素都插在最底层**（因为插入是逐个往数组末尾加的），
所以 n 个元素每个都要付 O(log n)：

```
T(n) = Σ(i=1 到 n) O(log i) = O(n log n)
```

**关键区别**：`sift_down` 建堆时，**底层的大量节点只需要下沉 0 到 1 层**（几乎不用动），
只有顶部的极少数节点需要下沉很多层。而 `sift_up` 建堆时，
**底层的大量节点每一个都要往上走满 log n 层**。这就是两者差一个 log 因子的根本原因。

**工程结论**：已有完整数组要变成堆，用 `std::make_heap`（O(n)），
不要循环 `push`（O(n log n)）。本章 `07_heap_and_priority_queue.cpp` 有实测对比。
</details>

### 题 7
`std::sort` 不稳定，`std::stable_sort` 稳定。
请给出一个**不稳定性会导致真实 bug** 的具体业务场景，
并说明为什么 `std::stable_sort` 实现代价更高。

<details>
<summary>答案</summary>

**真实场景：订单列表的二次排序。**

假设有一个订单列表，业务上要求：**先按金额从高到低排，金额相同时，
按下单时间从早到晚排（时间早的在前）**。

数据结构是 `struct Order { double amount; time_t created; std::string id; };`。

如果开发者这样写：

```cpp
// 第一步：先按时间排序（稳定排序）
std::sort(orders.begin(), orders.end(),
          [](const Order& a, const Order& b) { return a.created < b.created; });

// 第二步：再按金额排序
std::sort(orders.begin(), orders.end(),
          [](const Order& a, const Order& b) { return a.amount > b.amount; });
```

由于 `std::sort` **不稳定**，第二步在重排金额时，
对于金额相同的订单，它在分区和交换过程中会**打乱**第一步已经排好的时间顺序。
结果就是：金额相同的订单，其内部顺序是**未定义**的（取决于快排的划分过程、
数据规模、甚至 STL 版本），而不是按时间排好的。

这在业务上表现为：**每次刷新页面，同金额订单的顺序都可能不一样**。
如果这是一个「订单优先级队列」或者「结算顺序」，可能导致
**用户看到的顺序与后台处理顺序不一致**，甚至影响审计和对账。
而且这个 bug **极难复现和排查**，因为它在数据量小或数据恰好有序时不出现，
只在特定数据规模下才暴露。

**正确写法**（两种）：

```cpp
// 写法一：用 stable_sort（推荐）
std::stable_sort(orders.begin(), orders.end(),
                 [](const Order& a, const Order& b) { return a.created < b.created; });
std::stable_sort(orders.begin(), orders.end(),
                 [](const Order& a, const Order& b) { return a.amount > b.amount; });

// 写法二：一次排序，比较器里写全所有关键字（更高效，也是推荐做法）
std::sort(orders.begin(), orders.end(), [](const Order& a, const Order& b) {
    if (a.amount != b.amount) return a.amount > b.amount;   // 主关键字
    return a.created < b.created;                            // 次关键字
});
```

口诀：**多关键字排序，要么「从最后一个关键字开始依次用稳定排序」，
要么「在一个比较器里按优先级逐级比较」。**

**为什么 `std::stable_sort` 实现代价更高**：

1. **算法不同**：`std::sort` 用 introsort（快排 + 堆排 + 插入排序），
   原地排序，额外空间只有 O(log n) 的递归栈。
   而保持稳定性通常需要**归并类**算法——归并的过程必须保证
   「左边的元素在相等时优先」，这就需要**额外的 O(n) 缓冲区**来做归并。
2. **空间代价**：`std::stable_sort` 的标准复杂度是 O(n log n) 次比较，
   但如果**无法分配额外内存**，它会退化到 O(n log² n) 的原地归并版本。
   也就是说它的性能和可用内存相关，这一点和 `std::sort` 的确定性保证不同。
3. **性能代价**：归并排序的常数比快排大（需要额外的读写和内存带宽），
   而且在缓存局部性上通常不如精心优化的快排。

**工程结论**：**不需要稳定性时用 `std::sort`（更快）**，
需要时用 `std::stable_sort`（或写成单比较器的多关键字比较）。
关键是**要意识到 `std::sort` 不稳定**，别在依赖顺序的地方踩坑。
</details>

### 题 8
0-1 背包的一维滚动数组写法，为什么内层循环必须**倒序**遍历容量？
如果写成正序会发生什么？完全背包为什么又是正序？

<details>
<summary>答案</summary>

**先看二维方程。** 0-1 背包的状态定义是
「`dp[i][j]` = 只考虑前 i 件物品、容量为 j 时的最大价值」，转移：

```
dp[i][j] = max( dp[i-1][j],                        // 不放第 i 件
                dp[i-1][j - w[i]] + v[i] )         // 放第 i 件
```

**注意两个来源都是 `i-1`**——因为 0-1 背包规定每件物品**最多用一次**，
放了第 i 件之后，第 i 件就不能再放了，所以「放了第 i 件」这个状态
必须从「只考虑前 i-1 件」转移过来。

**压缩成一维。** 我们想省掉 i 这一维，用 `dp[j]` 表示「容量为 j 的最大价值」。
关键问题是：当我们计算 `dp[j]` 时，需要读的 `dp[j - w[i]]`
应该是**上一轮（i-1）的旧值**，还是**本轮（i）已经更新过的新值**？

对 0-1 背包，答案必须是**旧值**。

- **如果倒序遍历 j（从大到小）**：计算 `dp[j]` 时用到的 `dp[j - w[i]]`
  因为下标 `j - w[i] < j`，而我们是**从大到小**遍历的，
  所以那个位置**还没被本轮更新过**，读到的正是**上一轮的旧值**。
  这正好对应 `dp[i-1][j - w[i]]`，**语义正确**。

- **如果正序遍历 j（从小到大）**：计算 `dp[j]` 时，
  `dp[j - w[i]]` 因为下标更小，**已经在本次循环里被更新过了**，
  读到的是**本轮的新值**，也就是 `dp[i][...]`。
  这意味着「第 i 件物品已经被放进去过一次，现在又放一次」——
  **同一件物品被重复使用了**。这在数学上正好等价于
  「每件物品可以取无限多次」，也就是**完全背包**的转移方程：

```
dp[i][j] = max( dp[i-1][j], dp[i][j - w[i]] + v[i] )   // 注意这里是 i 不是 i-1
```

**所以完全背包的一维写法就是正序遍历**——因为它本来就要求
`dp[j - w[i]]` 是**本轮已更新**的值（表示「已经考虑过放这件物品，还可以再放」）。

**一句话总结**：
| 背包类型 | 转移方程第二项 | 需要读的值 | 一维遍历方向 |
| --- | --- | --- | --- |
| 0-1 背包 | `dp[i-1][j-w] + v` | 上一轮旧值 | **倒序** |
| 完全背包 | `dp[i][j-w] + v` | 本轮新值 | **正序** |

**记忆口诀**：**0-1 背包倒序（怕重复用），完全背包正序（就是要重复用）。**

**工程建议**：不要靠背这个结论。**先把二维方程写出来**，
然后问自己「`dp[j-w]` 应该是本轮还是上一轮的值」——
答案自然就出来了。记忆会错，方程不会骗你。

本章 `10_dynamic_programming.cpp` 会**故意把 0-1 背包写成正序**，
打印出错误结果与正确结果的对比，用可运行的证据说明这个坑是真的。

**推论**：同样道理，「零钱兑换求方案数」必须**外层遍历硬币、内层遍历金额**，
否则会把 {1, 2} 和 {2, 1} 当成两种不同的方案，导致重复计数。
**遍历顺序决定语义**，这是 DP 里最需要警惕的一类 bug。
</details>

### 题 9
Dijkstra 为什么不能处理负权边？请构造一个具体的小图说明它会给出错误答案。
有负权时应该用什么算法？它为什么能处理，代价是什么？

<details>
<summary>答案</summary>

**Dijkstra 的核心前提**：当算法从优先队列里取出距离最小的点 u 时，
就认为「源点到 u 的最短距离已经**最终确定**」，之后不再更新 u。

这个前提在**边权非负**时成立，理由是**单调性**：
所有边权 ≥ 0，所以「从源点出发，经过更多边」的距离只会不减。
既然 u 是当前未定点中距离最小的，那么任何「绕道经过其他未定点再回到 u」的路径
都只会更长，不可能得到比当前更短的距离。

**负权边破坏了这个单调性**。构造反例：

```
源点 S
边：S -> A  权重 2
    S -> B  权重 5
    B -> A  权重 -4        <-- 负权边
```

**正确的最短路**：
- S 到 B 是 5；
- S 到 A 可以走 S -> B -> A = 5 + (-4) = **1**，
  比直接 S -> A = 2 更短。所以 `dist[A] = 1`。

**Dijkstra 的执行过程**（用小顶堆）：
1. 初始 `dist = {S:0, A:∞, B:∞}`。堆里有 S(0)。
2. 弹出 S(0)，松弛它的邻居：`dist[A] = 2`，`dist[B] = 5`。堆里有 A(2)、B(5)。
3. 弹出距离最小的 **A(2)**，**把 A 定型**，不再更新。
   松弛 A 的邻居——A 没有出边，什么也不做。
4. 弹出 B(5)，松弛 B 的邻居：尝试 `dist[A] = min(2, 5 + (-4)) = min(2, 1) = 1`。
   **但 A 已经被定型了**，这一步更新要么被跳过，要么虽然更新了
   却**再也不会被重新处理**（因为 A 已经出过堆，不会再入堆）。

**Dijkstra 输出 `dist[A] = 2`，正确答案是 1 —— 错了。**

错误根源：算法在第 3 步就断言「A 的最短路确定了」，
但实际上是「先绕到 B 再走负权边回 A」更短。**贪心前提被负权破坏了。**

**有负权时用什么算法：Bellman-Ford。**
它的做法完全不同——**不假设任何点已经定型**，而是
「对所有边做松弛」这个动作重复 **V-1 轮**。

为什么是 V-1 轮？因为**在不存在负环的前提下，任何最短路径最多包含 V-1 条边**
（如果有 V 条边，说明路径上某个顶点重复了，即形成了环；
而从路径里去掉这个环不会让路径变长——因为环的权重非负。
所以最短路径一定是简单路径）。每一轮遍历所有边，
至少能确定「经过 k 条边的最短路」，k 轮后就能确定所有最短路。
复杂度 **O(V·E)**。

**Bellman-Ford 的额外能力：检测负环。**
在跑完 V-1 轮后，**再遍历一次所有边**。如果还能松弛成功
（即还存在 `dist[u] + w < dist[v]`），就说明存在**负环**——
沿这个环走一圈距离可以无限减小，「最短路径」根本不存在（趋于负无穷）。
这是一个非常有用的能力：Dijkstra 完全无法检测负环。

**代价**：O(V·E) 比 Dijkstra 的 O((V+E) log V) 慢得多，
尤其对稀疏图差距明显。所以**能用 Dijkstra 就不要用 Bellman-Ford**。

**补充优化**：
- **SPFA**（Shortest Path Faster Algorithm）是 Bellman-Ford 的队列优化版，
  只把「距离被更新的点」的邻居入队，平均快很多，
  但**最坏仍是 O(V·E)**，出题人可以用特殊数据卡掉它。
- **Johnson 算法**处理「稀疏图 + 有负权 + 要全源最短路」：
  先用 Bellman-Ford 计算一套「势能」h(v)，
  把每条边重赋权为 `w'(u,v) = w(u,v) + h(u) - h(v) ≥ 0`，
  然后对每个点跑一次 Dijkstra。总复杂度 O(V·E + V·E log V)。

**工程决策树**：
| 图的边权情况 | 用什么 | 复杂度 |
| --- | --- | --- |
| 无权 / 权都相同 | **BFS** | O(V+E) |
| 非负权，单源 | **Dijkstra + 堆** | O((V+E) log V) |
| 有负权，单源 | **Bellman-Ford**（顺便查负环） | O(V·E) |
| 有负权，全源，V 小 | **Floyd-Warshall** | O(V³) |
| 有负权，全源，稀疏 | **Johnson** | O(V·E log V) |
</details>

### 题 10
给定一个「从数据流中不断读取整数，随时查询已读数据的中位数」的需求，
请设计数据结构并说明复杂度。为什么不能用「维护一个有序数组」或「每来一个数就排序」？

<details>
<summary>答案</summary>

**双堆法（two heaps）**：维护两个堆，把数据分成大小相近的两半。

- **大顶堆 `low`**：存放**较小的一半**元素。堆顶是这一半里的**最大值**。
- **小顶堆 `high`**：存放**较大的一半**元素。堆顶是这一半里的**最小值**。

**不变式（必须始终维持）**：
1. `low` 中的所有元素 ≤ `high` 中的所有元素；
2. 两个堆的大小差不超过 1：`low.size() == high.size()` 或 `low.size() == high.size() + 1`。
   （约定让 `low` 多存一个，即 n 为奇数时中位数就是 `low.top()`。）

**插入 `add(x)` 的过程**：
1. 先压入 `low`（大顶堆）。
2. **平衡第一步**：如果 `low` 的堆顶 > `high` 的堆顶，
   说明 `low` 里有元素比 `high` 里的最小元素还大，
   违反了不变式 1。把 `low` 的堆顶移到 `high`（这样保证所有 `low` 元素 ≤ 所有 `high` 元素）。
   （`high` 为空时跳过这一步。）
3. **平衡第二步**：如果 `low.size() > high.size() + 1`，
   把 `low` 的堆顶移到 `high`，维持大小差 ≤ 1。

**查询 `median()`**：
- 如果 `low.size() == high.size()`（n 为偶数）：
  中位数 = `(low.top() + high.top()) / 2.0`；
- 如果 `low.size() == high.size() + 1`（n 为奇数）：
  中位数 = `low.top()`，**O(1)** 直接返回堆顶。

**复杂度**：
- `add`：两次堆操作（各自 O(log n)），所以 **O(log n)**；
- `median`：**O(1)**（只读两个堆顶）；
- 空间：**O(n)**。

**为什么不能用「维护一个有序数组」**：
如果用一个**有序数组**（每次都保持有序），查询中位数确实是 O(1)（取中间下标）。
但**插入**时，为了保持有序必须找到正确位置并把后面所有元素后移，
那是 **O(n)** 的搬移。在「数据流持续插入」的场景下，
n 次插入就是 **O(n²)**，完全不可接受。

**为什么不能「每来一个数就排序」**：
每次插入后都调用一次 `std::sort`，单次是 O(n log n)，
n 次插入总共 **O(n² log n)**，比有序数组还慢一倍多。
这是典型的「用错工具」：排序适合**一次性**处理整批数据，
不适合**逐条增量**维护。

**为什么双堆是最优解**：
双堆的关键洞察是：**求中位数并不需要全部数据有序，只需要知道
「中间那两个（或一个）元素是谁」**。所以我们把数据分成两半，
只需要每半的**边界元素**——也就是**堆顶**。
堆正好提供了「以 O(log n) 维护最值」的能力，
而取最值是 O(1)，所以整个方案达到 O(log n) 插入 / O(1) 查询。

**对比其他方案**：

| 方案 | 插入 | 查询中位数 | 说明 |
| --- | --- | --- | --- |
| 无序数组 + 每次排序 | O(1) | O(n log n) | 查询太慢 |
| 有序数组（插入时搬移） | O(n) | O(1) | 插入太慢 |
| 平衡 BST（带 size 计数） | O(log n) | O(log n) | 可行，但常数比堆大 |
| 跳表 | O(log n) 期望 | O(log n) 期望 | 可行 |
| **双堆** | **O(log n)** | **O(1)** | **最优且最简单** |

**工程建议**：
- 双堆法还可以方便地扩展到「求任意百分位数」（把两个堆的大小比例
  从 1:1 改成 p:(1-p)），也能扩展到「滑动窗口中位数」（配合惰性删除）。
- 实现细节：`std::priority_queue<int>` 默认是大顶堆，正好用作 `low`；
  `high` 需要小顶堆，用 `std::priority_queue<int, std::vector<int>, std::greater<int>>`。
  **注意 `std::greater` 的语义**——`priority_queue` 的 Compare 参数含义是
  「返回 true 表示 a 的优先级低于 b」，和 `std::sort` 的比较器**语义相反**，
  这是最容易写错的地方（本章 `07_heap_and_priority_queue.cpp` 专门讲了这个陷阱）。
- 本章 `07_heap_and_priority_queue.cpp` 里有完整的双堆实现和实测。
</details>

## 9. 结语

如果这一章只能记住三件事，就记这三件：

1. **选对数据结构和算法，比把代码写快重要一个数量级。**
   本章实测：n = 4000 时 O(n²) 已经比 O(n log n) 慢了约 100 倍，
   而且 n 越大差距越拉越开。先测再优化，先改算法再改代码。

2. **复杂度相同不代表性能相同。**
   `vector` 和 `list` 遍历都是 O(n)，实测差 20 倍，差在缓存局部性。
   所以「复杂度分析」决定的是**能不能用**，「实测」决定的是**谁更快**，
   两件事都要做。

3. **生产代码用 STL，手写是为了理解而不是替代。**
   STL 里有的，一律用 STL；STL 里没有的（并查集、图算法、专用结构），
   才自己写——而且要按本章的方式做**正确性对拍**和**性能实测**。

手写的真正价值在于：当 `std::unordered_map` 变慢时，
你知道那是负载因子和冲突的问题，知道该 `reserve`；
当 `std::sort` 在一个奇怪的数据集上表现异常时，
你知道 introsort 在什么条件下会切换到堆排序；
当有人提议「这里用链表吧，插入是 O(1)」时，
你能拿出实测数据说「不，先看看我们的访问模式」。
